# PROJECT_HANDOFF — Калькулятор доставки (СДЭК + Деловые Линии)

Документ передачи проекта. Состояние кода зафиксировано на коммите
`47b96b1` (июль 2026); `PROJECT_HANDOFF.md` создан локально и ещё не
добавлен в Git. Секретов в документе нет — только имена переменных окружения.

## 1. Что это

Внутреннее веб-приложение для менеджеров отдела продаж. Менеджер вводит
артикулы и количества (или ручные места), приложение по справочнику из
Google Таблицы рассчитывает упаковочные места и запрашивает стоимость и
сроки доставки у двух транспортных компаний: **СДЭК** и **Деловые Линии**.

Продакшен разворачивается с GitHub (`ropuwz-dot/calc_sdek`) на VPS
с Ubuntu (Node + systemd + nginx + HTTPS). Инструкция — в README, раздел
«Деплой на VPS».

## 2. Стек

| Слой | Технология |
|---|---|
| Фреймворк | Next.js 16 (App Router, Turbopack), TypeScript strict |
| UI | React 19, один клиентский компонент-калькулятор, чистый CSS (globals.css) |
| Google API | googleapis (Sheets v4, OAuth 2.0) |
| Сессии | jose (JWE A256GCM в httpOnly-cookie), самописный OAuth-флоу (не next-auth) |
| БД | **Нет.** Все данные — Google Sheets и API перевозчиков; кэши в памяти процесса |
| Тесты | Нет постоянных. Проверки делались временными self-test роутами против живых API (удалены) |

## 3. Модель доступа (ключевая концепция)

**Право пользоваться приложением = доступ к Google Таблице.**

1. Пользователь входит через свой Google-аккаунт (OAuth, scopes:
   `openid email profile spreadsheets.readonly` — Drive-доступ не запрашивается).
2. Сервер читает метаданные таблицы **токеном пользователя**. Читается —
   доступ есть; 403/404 — страница «Нет доступа к таблице».
3. Владелец таблицы управляет доступом кнопкой «Поделиться». Отдельного
   списка пользователей в приложении нет. Service account не используется.

Сессия — httpOnly-cookie с шифрованным JWE (ключ из `NEXTAUTH_SECRET`);
внутри access/refresh token Google. Access token продлевается по refresh
token прозрачно (`lib/googleAuth.ts:getValidAccessToken`), повторный вход —
раз в 30 дней. OAuth-флоу защищён `state` (сравнение через `timingSafeEqual`)
и проверкой выданных scopes прямо в callback (Google показывает разрешения
галочками, снятыми по умолчанию — если галочку таблиц не отметили,
пользователь получает понятное сообщение сразу).

## 4. Архитектура

```
Browser (components/Calculator.tsx — client component, без секретов)
   │ JSON: /api/*
   ▼
Next.js server (все секреты и интеграции только здесь)
 ├─ lib/apiAuth.ts      гвард всех API: сессия → живой токен → доступ к таблице
 │                      (вердикт кэшируется 60 с по SHA-256 access token'а)
 ├─ lib/session.ts      JWE-cookie сессии
 ├─ lib/googleAuth.ts   OAuth: вход, обмен кода, refresh
 ├─ lib/googleSheets.ts чтение таблицы токеном пользователя (readonly)
 ├─ lib/catalog.ts      адаптивный парсер справочника + отчёт качества данных
 ├─ lib/packing.ts      чистый модуль упаковки (см. §6)
 ├─ lib/manualPlaces.ts общая валидация «ручных мест»
 ├─ lib/cdek.ts         СДЭК v2: OAuth-токен (кэш), tarifflist, города, ПВЗ+лимиты,
 │                      геокодинг улиц через OSM Nominatim для «ближайших ПВЗ»
 ├─ lib/dellin.ts       ДЛ: сессия по PAT (кэш 25 дн + 1 ретрай), КЛАДР-города/улицы,
 │                      терминалы, калькулятор v2 (см. §7 — важные особенности)
 └─ lib/dadata.ts       DaData: подсказки улиц для адресов СДЭК (опционально)

API-роуты (все за requireSheetsUser):
 /api/auth/{signin,callback,signout}      OAuth
 /api/products/search                     поиск по каталогу (кэш каталога 60 с)
 /api/pack                                расчёт мест без ТК
 /api/quote                               СДЭК: свежий каталог → упаковка → tarifflist
 /api/locations, /api/pvz, /api/streets   подсказки СДЭК (города, ПВЗ, улицы DaData)
 /api/dellin/{locations,streets,terminals,quote}   аналогично для ДЛ

Страницы:
 /                        вход → калькулятор → или «Нет доступа»
 /admin/google-sheets-check  диагностика доступа и структуры таблицы
 /admin/data-quality         отчёт качества данных справочника
```

**Принцип «не доверять фронту»**: клиент отправляет только артикулы,
количества и направления. Перед каждым расчётом (`/api/quote`,
`/api/dellin/quote`) сервер заново читает таблицу токеном пользователя
(без кэша) и пересчитывает места. Ручные места валидируются на сервере
(габариты ≤1000 см, вес ≤10 т, count ≤1000, максимум 100 мест/позиций).

## 5. Справочник (Google Таблица)

ID таблицы задаётся `GOOGLE_SHEET_ID`. Структуру таблицы приложение
**не меняет** (scope readonly) — парсер (`lib/catalog.ts`) адаптируется:

- ходит по всем листам, ищет блоки по строкам-шапкам;
- блок «Артикул + ДШВ/вес» без количества → основной справочник;
- блок с колонкой «Количество в упаковке» → правила групповой упаковки;
  строки такого блока с ПУСТЫМ количеством → товарные строки (гибридные
  листы типа «Справочник (моно)» — реальный кейс);
- блоки с «Место/Откуда/Куда/Тариф/Стоимость/ИТОГО» → расчётные, пропускаются;
- данные одного артикула из разных блоков сливаются (пустые поля дополняются,
  конфликты значений фиксируются в отчёте качества);
- единицы: «, м» в шапке → ×100 в см; запятая как десятичный разделитель.

Все проблемы данных не роняют работу, а видны на `/admin/data-quality`.

## 6. Бизнес-логика упаковки (`lib/packing.ts`)

Для каждой позиции:
1. Точное правило на всё количество → одно место.
2. Иначе жадная раскладка правилами от большей упаковки к меньшей.
3. Остаток — **стопкой в одно место**: единицы складываются вдоль
   наименьшего габарита, вес/объём суммируются; стопка выше 150 см
   делится на несколько примерно равных (константа `MAX_STACK_CM`).
4. Нет правил, но есть ДШВ+вес единицы → весь объём поштучно (стопками)
   с предупреждением.
5. Нет ни правил, ни полных данных → понятная ошибка, расчёт блокируется.
6. Места с нулевым весом/габаритом в ТК не отправляются.
7. В СДЭК вес уходит в граммах, габариты в целых см (ceil).

## 7. Интеграции с ТК — важные особенности (добыты отладкой!)

### СДЭК (lib/cdek.ts)
- OAuth client_credentials, токен кэшируется до истечения.
- `/calculator/tarifflist`: все тарифы, фильтр по режиму
  (`delivery_mode` 1–4 = дверь-дверь … склад-склад), сортировка по цене.
- **Цены СДЭК приходят БЕЗ НДС** (бизнес-правило заказчика: НДС 22%
  начисляется сверху; константа `VAT_RATE` в Calculator.tsx).
- ПВЗ: `/deliverypoints?city_code&type=PVZ`, у пунктов есть лимиты веса
  на место (и габариты ячеек). Реализовано: сводная проверка по городу,
  выбор конкретного ПВЗ с проверкой его лимитов, подбор ПВЗ по улице
  (substring по адресам → если пусто, геокодинг улицы через **OSM
  Nominatim** и ближайшие ПВЗ с расстоянием). Лимиты — на ОДНО место;
  для крупных отправок (>10 мест или >300 кг) отдельное предупреждение.
- Подсказки улиц для адресов «дверь» — **DaData** (опционально,
  `DADATA_API_KEY`; без ключа поле остаётся свободным текстом).

### Деловые Линии (lib/dellin.ts)
- Авторизация: PAT → `/v4/auth/login.json` → sessionID (кэш 25 дней;
  при ошибке сессии кэш сбрасывается и запрос повторяется один раз —
  `postDellinWithSession`).
- Города/улицы — КЛАДР-методы ДЛ; для «двери» улица+дом обязательны
  (валидируется и на клиенте, и на сервере).
- Терминалы: `/v1/public/request_terminals.json` по городу и габаритам;
  вариант `terminal` в калькуляторе требует `terminalID` (город не принимает).
- **ГЛАВНАЯ ЛОВУШКА**: в ответе `/v2/calculator.json` поле
  `availableDeliveryTypes` содержит стоимость ТОЛЬКО межтерминальной
  перевозки по каждому виду. Полная цена собирается так:
  `data.price` (итог для выбранного вида, включает забор/доставку по
  городу, страхование, сервисы) с подстановкой межтерминальной части
  нужного вида. Расшифровка составляющих показывается в таблице тарифов.
- **Цены ДЛ уже включают НДС** (подтверждено заказчиком) — НДС сверху
  не начисляется.
- `cargo.insurance.statedValue` калькулятор **игнорирует** (проверено
  эмпирически на нескольких маршрутах) — страхование груза и срока ДЛ
  считают сами и включают в `price`; поэтому поля «объявленная стоимость»
  в UI нет, а страховка видна в расшифровке.
- Сроки: `deliveryTerm` ДЛ возвращают нулевым; срок считается от «сегодня»
  до даты выдачи получателю / отвоза на адрес (поля `orderDates.*`,
  для терминальной и адресной доставки поля разные). Семантика —
  «дней до получения груза клиентом» (решение заказчика, вариант 1);
  у СДЭК же `period_min/max` — «дней в пути», сравнение слегка льстит СДЭК.
- Допуслуги оформления (ПРР/подъём на этаж и т.п.) калькулятор НЕ считает —
  об этом есть подсказка в UI; расхождение со счётом ЛК на эти суммы — норма.

### Финансовые правила UI
- Колонки СДЭК: Стоимость → НДС 22% (сверху) → Итого; ДЛ: «Стоимость с НДС» → Итого.
- Переключатель «Платит клиент» добавляет +5% к итогу (`CLIENT_PAYS_MARKUP`).
- Сравнительная таблица «лучший тариф СДЭК vs ДЛ» появляется, когда
  посчитаны обе ТК.

## 9. Запуск

Локально: `npm install && npm run dev` → http://localhost:3000
(нужен `.env.local`; после его изменения — перезапуск). Прод-сборка:
`npm run build && npm start`. HTTPS в проде обязателен (Secure-cookie).
Полная инструкция по VPS (Node 22, systemd-юнит `deploy/cdek-calculator.service`,
nginx `deploy/nginx-example.conf`, certbot) — в README. Обновление:
`git pull → npm ci → npm run build → systemctl restart cdek-calculator`.

Требования VPS: 1 vCPU / 1 ГБ RAM + 2 ГБ swap (сборка прожорливее рантайма),
исходящий HTTPS к `*.googleapis.com`, `api.cdek.ru`, `api.dellin.ru`,
`nominatim.openstreetmap.org`, `suggestions.dadata.ru`.

## 10. Известные проблемы и ограничения

1. **🔴 Секреты требуют ротации.** Все ключи (Google client secret, креды
   СДЭК, PAT ДЛ, ключи DaData) передавались в переписке при разработке.
   Перевыпустить всё и обновить `.env.local` на сервере и локально.
2. **🔴 Доступ к таблице «Все, у кого есть ссылка — Редактор»** (на момент
   передачи владелец планировал закрыть). Пока открыт — проверка доступа
   пропускает ЛЮБОЙ Google-аккаунт, и любой владелец ссылки может править
   справочник. Сменить на «Ограниченный» + поимённые доступы.
3. OAuth consent screen в режиме Testing: каждого менеджера нужно добавлять
   и в доступы таблицы, и в Test users. Для масштабирования — публикация
   приложения (Google потребует верификацию из-за scope таблиц).
4. Расчёт ДЛ не включает допуслуги оформления (ПРР и пр.) и может расходиться
   со счётом ЛК на их сумму; также ДЛ могут применить больший расчётный
   объём (см. кейс 0,1 м³ в счёте против фактических 0,0243 м³).
5. PAT ДЛ без привязанного контрагента (`customers.json` пуст) — расчёт
   по публичным ценам; если у ЛК появится договор со скидками, перевыпустить
   PAT с привязкой к контрагенту.
6. Лимиты ПВЗ СДЭК — на одно место; суммарный объём отправки пункты не
   декларируют (есть эвристическое предупреждение о крупных отправках).
7. Кэши в памяти процесса (каталог 60 с, доступ 60 с, ПВЗ 6 ч/100 городов,
   геокод 500 записей, токены/сессии ТК) — при нескольких инстансах Node
   не разделяются; текущий деплой — один процесс, это ок.
8. Постоянных автотестов нет — критичная логика проверялась временными
   self-test роутами против живых API (в истории коммитов их нет, паттерн
   описан ниже). Стоит завести юнит-тесты хотя бы на `packing.ts` и
   `catalog.ts` — они чистые и легко тестируются.
9. Nominatim (геокодинг) — публичный сервис с лимитом ~1 rps; для текущей
   нагрузки достаточно, при росте заменить (например, на DaData-геокодер).
10. `next lint` не настроен (ESLint-конфига нет); проверка типов —
    `npx tsc --noEmit`.

## 11. Текущее состояние и следующие шаги

**Реализовано в коде:** две независимые вкладки расчёта: СДЭК и Деловые
Линии, общий набор позиций/мест, ручные места, выбор города, адреса или
терминала и сравнительная таблица. Последний коммит исправляет расшифровку
страхования ДЛ. Текущая ветка не содержит изменений исходного кода; сам этот
handoff-файл пока не отслеживается Git.

**Перед запуском новой командой:** нужно выполнить end-to-end проверку на
локальном окружении и отдельно на VPS с действующими учётными данными. В
репозитории нет автоматизированного тестового набора, поэтому нельзя считать
боевой статус интеграций подтверждённым только по исходному коду.

**Текущая продуктовая задача: Magic Trans (ещё не начата).** Добавить третью
ТК, не ломая независимые расчёты СДЭК и ДЛ. Из изученной документации:

- калькулятор: `POST /prc/hs/EcommAPI/v1/calculator`;
- справочники: `GET /prc/hs/EcommAPI/v1/territory` и
  `GET /prc/hs/EcommAPI/v1/terminal`;
- авторизация вынесена в Security API: refresh/access-токены, а запросы к

Сохранённые HTML-страницы Swagger не содержат JSON-схемы запросов для
`/auth`, `/access` и `/refresh`. До реализации требуется получить исходные
OpenAPI JSON-файлы или подтвердить форматы у поддержки Magic Trans; без этого
нельзя корректно реализовать серверное получение и обновление access-токена.

## 12. Как здесь принято работать (соглашения)

- Все серверные модули начинаются с `import "server-only"` — случайный
  импорт в клиентский код ломает сборку, а не утекает секретом.
- Каждый API-роут первой строкой вызывает `requireSheetsUser()`.
- Ошибки внешних API переводятся в человеческие русские сообщения;
  роуты всегда отвечают JSON (клиентский `parseJson` дополнительно
  устойчив к HTML-подменам от прокси).
- Токены и секреты не логируются нигде.
- Паттерн проверки: временный роут `app/api/dev-selftest/route.ts` с
  проверками против живых API → прогон → удаление до коммита.
- Коммиты — по фиче, с содержательным описанием (см. `git log`).
